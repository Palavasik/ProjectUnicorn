# Что делать дальше: план с минимальным вмешательством

Краткий обзор текущего состояния и пошаговый план действий. Цель — один раз настроить окружение и инфраструктуру, после чего деплой идёт автоматически (push → Railway).

---

## 1. Что уже сделано в проекте

- **Бот**: поиск маршрутов (геолокация → дистанция → OpenAI → список маршрутов → ссылка в Яндекс.Карты), обратная связь после выбора маршрута.
- **Навигация**: на шаге «Локация» — кнопка «Назад» (в главное меню); на шаге «Дистанция» — «← Назад» (к вводу точки) и «В начало».
- **Supabase**: сохранение пользователей при `/start` и отзывов после выбора маршрута; клиент в коде, схема в `scripts/supabase_schema.sql`.
- **Railway**: `Procfile`, `railway.json`; бот запускается по push, режим webhook при заданных `PORT` и `WEBHOOK_URL`.

---

## 2. Ваши действия (один раз, минимум шагов)

### Шаг A: Supabase (≈5 минут)

1. Зайти на [supabase.com](https://supabase.com), войти или зарегистрироваться.
2. **New Project** — имя, пароль БД, регион → дождаться создания.
3. **Settings** → **Database**: в блоке **Connection string** скопировать **URI** (подставить пароль БД). Это **`DATABASE_URL`** для Railway. При задании `DATABASE_URL` миграции выполняются при старте бота, таблицы создавать вручную не нужно.
4. (Опционально) **Settings** → **API**: скопировать **Project URL** и **service_role** — нужны только если **не** используете `DATABASE_URL` (режим REST).

### Шаг B: Railway (≈3 минуты)

1. Открыть [railway.app](https://railway.app), проект с ботом (или создать проект и подключить репозиторий GitHub).
2. У сервиса бота открыть **Variables** и задать переменные (список в **`scripts/railway_env_example.sh`**):

   - `BOT_TOKEN` — токен от @BotFather  
   - `OPENAI_API_KEY` — ключ OpenAI  
   - `WEBHOOK_URL` — URL сервиса (Railway → **Generate Domain**)  
   - **`DATABASE_URL`** — строка подключения PostgreSQL из Supabase (шаг A.3). Тогда миграции применятся при старте, таблицы создавать вручную не нужно.  
   - Либо вместо `DATABASE_URL`: `SUPABASE_URL` и `SUPABASE_SERVICE_KEY` (тогда один раз выполнить `scripts/supabase_schema.sql` в SQL Editor).  

3. Сохранить. Railway сам сделает редеплой.

Если домен ещё не создан: **Settings** → **Generate Domain**, затем подставить полученный URL в `WEBHOOK_URL`.

### Шаг C: Проверка

1. В Telegram написать боту `/start` — в Supabase в **Table Editor** → таблица **users** должна появиться запись.
2. Пройти сценарий: «Найти маршрут» → точка старта → дистанция → выбор маршрута → оценка. В таблице **feedback** должна появиться запись.

На этом минимальная настройка заканчивается. Дальше достаточно пушить в ветку, к которой подключён Railway, — деплой будет автоматическим.

## 3. Автоматизация (по желанию)

Чтобы ещё уменьшить ручные действия и риск ошибок, можно добавить следующее.

### 3.1 Проверка переменных перед запуском

Скрипт или код при старте бота может проверять наличие обязательных переменных (`BOT_TOKEN`, `OPENAI_API_KEY`, `WEBHOOK_URL` при деплое; опционально `SUPABASE_URL` / `SUPABASE_SERVICE_KEY`) и выводить понятное сообщение, чего не хватает. Тогда при падении на Railway сразу видно, какую переменную добавить.

### 3.2 CI (GitHub Actions)

- На каждый push/PR: установка зависимостей, линтер (flake8/black), тесты (pytest).  
- Это не заменяет деплой на Railway, но снижает риск задеплоить сломанный код.  
- Деплой по push в `main` уже делает Railway (если репозиторий подключён к проекту).

### 3.3 Миграции БД и ORM

- **Сейчас**: схема БД задаётся один раз скриптом **`scripts/supabase_schema.sql`** в Supabase SQL Editor; бот работает через клиент Supabase (REST), без ORM.
- **ORM** (например SQLAlchemy + Alembic) имеет смысл подключать, если:
  - появятся сложные запросы или связи между таблицами;
  - нужны версионированные миграции (каждое изменение схемы — отдельный файл и применение через CLI).
- Для текущего сценария (две простые таблицы, вставка/обновление из бота) Supabase-клиента достаточно; добавление ORM можно отложить.

Если позже решите ввести миграции:

- Вариант 1: оставить Supabase и использовать [Supabase CLI](https://supabase.com/docs/guides/cli) (миграции в репозитории, применение через `supabase db push` или вручную в Dashboard).  
- Вариант 2: перейти на прямое подключение к PostgreSQL (connection string из Supabase), тогда можно добавить SQLAlchemy + Alembic и хранить миграции в репозитории; применение — через скрипт или CI.

## 4. Порядок действий (кратко)

| # | Действие | Где | Время |
|---|----------|-----|-------|
| 1 | Создать проект Supabase | supabase.com | 2 мин |
| 2 | Выполнить `scripts/supabase_schema.sql` в SQL Editor | Supabase Dashboard | 1 мин |
| 3 | Скопировать Project URL и service_role key | Supabase → Settings → API | 1 мин |
| 4 | Задать переменные окружения (в т.ч. Supabase) | Railway → Variables | 2 мин |
| 5 | При необходимости создать домен и подставить его в `WEBHOOK_URL` | Railway → Settings | 1 мин |
| 6 | Проверить: `/start` → запись в `users`; полный сценарий → запись в `feedback` | Telegram + Supabase Table Editor | 2 мин |

Дальше: правки в коде → push в ветку → Railway сам деплоит. Дополнительно можно ввести проверку env (п. 3.1) и CI (п. 3.2); ORM и миграции — по необходимости (п. 3.3).
